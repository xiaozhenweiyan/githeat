## 正文

### 起因

事情起因很简单：我想知道「哪些文件最容易出 bug」。

这个问题有二十年的研究背书——**一个文件的修改频率，比它的代码复杂度更能预测缺陷**。圈复杂度只告诉你这个文件「可能」难；churn（改动热度）告诉你这个文件**正在**被人反复打开、反复改坏。

市面上有商业工具做这个（CodeScene），开源的只有零散 shell 脚本。所以我让 AI 写了一个零依赖的 CLI：`githeat`。它读 git 历史，给每个源码文件算一个 0–100 的热点分，终端出彩色热力表，还能导出可以直接嵌 README 的 SVG 热力图。

**到这里为止，一切都很顺利。问题出在我决定验证它的时候。**

### 第一步：我给自己设计了一个「标准答案」

怎么知道一个工具指的方向对不对？我需要一个外部的、不依赖工具本身的答案。

我想到的办法是：**看作者自己后来修了哪里。**

具体做法：
1. 取某个开源项目的两个版本（比如 v5.0.0 和 v5.1.0）
2. 把这两个版本之间、**提交信息被作者描述为修复类**的提交（`fix:` / `refactor:` / `optimize` / `performance`）碰过的文件，当作「标准答案」
3. 然后**只用较早版本的历史**排名，看这些文件排得高不高

### 第二步：差点被自己骗过去

第一版的评测结果是「答案组的平均百分位比对照组高 22.9 个百分点，富集 1.6 倍」。

看起来挺好。**但这里有个陷阱**：被修过的文件，**天然就是最近被改过的文件**，而我的评分里有「近期加成」。也就是说，我测出来的可能只是「最近活跃度」，不是「诊断能力」。

所以我加了对照组：**同一区间内被普通提交碰过的文件**。两组一样近期活跃，只有「被关注的方式」不同。

**这一步是整件事里最重要的设计决定。**

### 第三步：加对照组之后，出现了一个更难看的结果

我把绝对精度算了出来——不问「相对提升多少」，而问「**你点开前 10 个文件，几个是对的**」：

| 项目 | 随机抽 | 按提交次数排序 | 本工具 |
|---|---:|---:|---:|
| express（6173 提交）| 0.97 / 10 | **3.33 / 10** | **3.33 / 10** |
| chalk（380 提交）| 2.19 / 10 | **2.67 / 10** | **2.67 / 10** |
| slugify（78 提交）| 2.33 / 10 | **2.33 / 10** | **2.33 / 10** |

注意第三列和第四列：**一模一样**。

「按提交次数排序」就是这一行：

```bash
git log --name-only | sort | uniq -c | sort -rn
```

**我这个带加权、对数归一化、近期系数的评分公式，和这行命令命中数完全相同。**

### 第四步：为什么必然相同

我去查了同口径下的排序重合度：

```
前 10 名重合度：10.0 / 10
```

**完全一致。** 然后我回去看自己的公式：

```
score = 100 × (0.68 × churn + 0.32 × changes) × recency
```

- `churn` 我定义成「文件在每次提交中被修改的累计次数」——**它就是提交次数**
- `changes` 是「多少个提交碰过它」——**还是提交次数**
- 对数归一化是**单调变换，不可能改变顺序**
- `recency` 是唯一可能改变顺序的项，在这些仓库上没起作用

**所以这个评分函数在数学上退化成了「按提交次数排序」。** 我写的 68/32 加权、90 分位锚点，全是装饰。

### 第五步：我改了默认值，并用同一套评测验证改动

既然复杂公式没价值，那就把默认改成有证据支持的那个：

```bash
githeat --score commits      # 新默认：100 × (本文件改动数 ÷ 最忙文件的改动数)
githeat --score composite    # 旧公式，保留但不作默认
```

然后重跑评测，确认这次改动的代价是零：

| 项目 | 模式 | 随机 | 按次数排序 | 本工具 |
|---|---|---:|---:|---:|
| express | commits | 0.97/10 | 3.33/10 | **3.33/10** |
| express | composite | 0.97/10 | 3.33/10 | **3.33/10** |
| chalk | commits | 2.19/10 | 2.67/10 | **2.67/10** |
| chalk | composite | 2.19/10 | 2.67/10 | **2.67/10** |

**两个公式、六次测量、零差异。**

### 那这个工具还有用吗

有，但**不是我原本宣称的那个用处**。诚实的清单：

**成立的：**
- 比随机好 3.4 倍（express 上 3.33 vs 0.97）——信号是真的，只是很弱
- **精度集中在最头部**：express 上前 5 名有 **53%** 是对的。**当「看这 5 个」用有价值**
- 它**不是**「最近改动检测器」（对照组证明了这点）
- 有几个**不依赖排名**的功能，回答的是提交次数回答不了的问题：
  - `githeat lines <文件>`：一个热点文件，**哪一段**在动。实测形状是这样的——
    ```
    most untouched: lines 1-242 (242 lines) — nothing here for about 900 days
    newest work:    lines 243-302 (60 lines) — last touched 4 days ago
    ```
    编辑一个热点文件之前，知道「新鲜的 60 行是活跃区，老的 242 行最容易让你意外」比知道它的总分有用。
  - `githeat roots`：**几个热点文件共同依赖谁**。这个功能在 githeat 自己的仓库上找出来一个 **43 分**（排名根本不在意）的文件，而它是**多个高分热点共同依赖的模块**——这正是你说的"反推根源"。
  - `--base <分支>`：这次改动让哪些文件变热了
  - PR 机器人：自动在 PR 里标出"你改的文件是已知热点"

**不成立的：**
- ❌ 「找到你的问题文件」——找不到，精确率 33%
- ❌ 「复杂评分有价值」——和一行 shell 命令一样
- ❌ 召回率只有 9%——**不能当清单用**

### 我学到的三件事

**1. 相对指标可以掩盖一切。**
「富集 1.6 倍」听起来不错，但它和「和零成本基线打平」完全不矛盾。**只有绝对精度能拿来做决定。**

**2. 加对照组是必须的，不是可选的。**
如果我只跟「仓库里其他文件」比，测出来的全是近期活跃度。**任何声称能预测的东西，都得跟同样条件的对照比。**

**3. 用 AI 写工具，最大的风险不是它写错代码，是它（和你）倾向于相信它有用。**
AI 可以很快写出一个「看起来很合理」的评分公式，而合理性是没有价值的——**要么有证据，要么删掉**。

### 最后

项目在这里，MIT，零依赖：

**https://github.com/xiaozhenweiyan/githeat**

README 第一屏就是那张不利的评测表。我知道这不利于推广，但**一个把「我的评分和一行 shell 命令打平」写在首页的工具，比一个吹自己的工具更值得你花五分钟**。

如果你有重构历史清晰的项目，跑一下这个命令，把表格贴给我——这是这个项目唯一无法自己生成的那类证据：

```bash
node scripts/eval-precision.mjs /path/to/your/repo --pairs 4
```

### 附：一个数字会漂移的提醒

上面那张评测表里的数字（0.97 / 3.33 / 3.33 等）**会随项目自身变化**——我改了一次评分默认值，
`githeat roots` 找出来的"共享根源"就从「6 个热点 554 分」变成「5 个热点 333 分」。

所以文章里我只保留了**结构性结论**（两个公式命中数相同、前 5 名精确率 53%），
具体数字以仓库里的 `docs/evaluation.md` 为准——那份是每次评测后更新的。

**这也是我给所有引用了数字的文章的建议：别把会变的数字当论据，把不会变的结构当论据。**
